🔋 Metrics & Methods — the science

How discharge speed / aging are computed, and what the versions, metrics and deltas actually differ in.

0. How the data is produced

Every minute the battery is recorded with ioreg. Analysis uses only discharge spans (charger unplugged ac=false, level monotonically decreasing, adjacent-sample gap ≤ 2 min). Between two adjacent samples we assume a straight line (your proposed assumption), and slice finely at 1% and date boundaries, accumulating drop (Δ%) · time · energy (W·s) into each (date, 10% band) cell. This "clipped interval accumulation" is the foundation of every calculation.

Reporting gate: to show a cell it needs observed ≥ 10 min & total drop ≥ 2%p & ≥ 3 bands. Below that it's emptied as "insufficient data" (so little data can't fabricate a fake trend).

📐 Measurement sources & refresh rates — why this app is more accurate

Values come from two sources of different character. Power updates in real time from the SMC at ~1 s (≈1 Hz); charge level updates from ioreg at ~60 s. This app samples the SMC every 0.5 s and records the time-weighted average power over the last minute (∫W dt / 60 s) — so a brief spike can't distort a whole minute, making it more accurate than apps that read a single instantaneous value. (Because the SMC is ~1 Hz, a 2 s poll can miss values, so we sample densely at 0.5 s.)

Charge level, voltage and % are refreshed by the battery's gauge IC at ~60 s, so they're recorded at that cadence. rawCap is an integer mAh, so its true resolution is 1 mAh ≈ 0.022% (rawMax ≈ 4600) — about 46× finer than macOS's integer % (1% steps), which is what makes the level-change (%/min) curve smooth and precise.

1. Metrics: speed (%/min) vs aging (Wh/%)

They answer different questions.

Speed — %/min (negative = discharge)

speed = −60 × Σ(drop %) ÷ Σ(time sec)

How fast battery % falls per minute. It's a "felt speed" that mixes load (how much you use) + aging. Even the same new battery gets faster under heavy CPU use. → Answers "why is it draining fast right now?".

Aging — Wh/% (lower = more aging)

In one line — Wh/% = "how much real energy 1% holds" (≈ full capacity ÷ 100)

Wh/% = Σ(energy Wh) ÷ Σ(drop %)

The energy it actually took to drain 1%. Physically 1% ≈ (full energy)/100, and as a battery ages its full capacity (mAh) shrinks, so the energy in 1% shrinks too. So Wh/% is nearly independent of load (using a lot and draining fast doesn't change the "energy per 1%") → a pure aging metric with load removed.

ObservationInterpretation
Speed ↑ but Wh/% unchangedBattery is fine; it got faster because load (usage) rose
Speed ↑ and Wh/% ↓Real battery aging is underway

Level toggle integer % ↔ mAh precise: pct is 1% steps (coarse), rawCap/rawMax is ~0.02% resolution (precise). Precise mode reduces quantization noise, so V4c·V5 stabilize.

2. Speed methods (versions): V4a · V0 · V1 · V4c · V5

Data crossing one band (e.g. 90–100%) is clipped at the ends (starts at 93%, stops at 78%) and samples are uneven. "The average speed of that band" depends on how you estimate it — that's the difference between versions. The same data is computed several ways to compare how much the estimation method changes the result.

VersionMethodCharacter / when
V4a Pooled (default)−Σ(drop) ÷ Σ(time) "total drop over total time spent in the band"A sum of ratios, so it's invariant to how you segment; short noisy stretches don't spike. Statistically most robust → the default.
V0 Raw meanCompute each discharge episode's speed separately and take a simple averageThe ratio-average trap: a short, noisy episode carries the same weight as a long one → biased. For contrast/reference.
V1 Full-band onlyAverage only episodes that crossed exactly 10%↔10% fullyClean but selection bias: only long single-sitting sessions survive; short ones are thrown out.
V4c 1% sub-binsSplit the band into 1% pieces, get each 1%'s speed, and average the 1%s equally"Level-based standardization". Diagnoses partial-coverage (e.g. only starts at 93%) and data-skew bias. Noise-sensitive at integer %.
V5 RegressionRegress (least-squares) a line through every raw point in the band, take the slopeUnsuited to integer %, autocorrelation and step shapes (expert consensus) → diagnostic. More meaningful at mAh precise.

How to read it: normally use V4a. If V0/V1 diverge a lot from V4a, that signals "estimation is unstable" (many short sessions). If V4c differs a lot from V4a, "data is skewed to one side within the band". (That's why the main table shows only V4a; the rest are for diagnosis.)

3. What is the delta (Δ) relative to

The delta re-expresses each band as its difference from "that band's own initial baseline".

  • baseline = the median of the earliest 20% of the periods of that band's data, sorted by time.
  • displayed value = (current value) − (that band's baseline)

Why: absolute speed differs per band (per-band offset), making trend comparison hard. The delta subtracts that offset and keeps only "how much it changed vs. the start". Below 0 means — in the speed metric, faster than the start; in the Wh/% metric, more aged than the start. (Delta color is a diverging scale around 0: red = worse, blue = better.)

4. Period: day / week / month

The same V4a pooling is re-accumulated from the raw data over a wider period (not by averaging daily values — that would bias it). Toward week/month, noise falls and the long-term aging trend sharpens. (The gate amount is the same, so wider periods pass more easily.)

5. How to read the screens

  • Heatmap: x = date, y = band, color = value, opacity = observed amount (fainter = less data), teal line = health. Green on the left → red on the right means getting faster / aging. Click a cell = that date's cross-section.
  • 3D: x = date, height = value, depth = band (level). Shapes: Lines (per-band time trend) · Ridges (per-date profile) · Lines+Ridges (grid) · Surface (terrain). The 0 line = where speed is 0 (no discharge); Delta · Expand toggles.
  • Bottom-left table: click a row (band) → that band's trend. Empty dates are not filled in (no interpolation — we don't invent missing data).

6. The main 3D graph's vertical axis · markers

The main 3D graph (x = time of day, depth = date) lets you switch the vertical axis three ways.

  • Battery % — level at that moment. Follows the global precision setting (precise mAh / integer %).
  • Power W — pick battery / system / adapter via "Power rail" below. The battery rail is a signed axis (charge +, discharge −).
  • Δ charge %/min — explained below.

Δ charge %/min = d(level)/dt · trailing moving average

Each point's value is the average rate over the smoothing window (e.g. 20 min) just BEFORE that point — a trailing moving average that looks only at the past, so it never uses future values. So picking 20 min means "the average speed over the past 20 min", not a centered average of "past 10 min + future 10 min".

rate(t) = ( level(t) − level(t − window) ) ÷ window(min)

Sign: + charge, − discharge (above/below the 0 line). A narrower window is twitchier (variation shows), a wider one is smoother. Raw level (integer %) is 1% steps, so differentiating it directly makes a sawtooth; the window smooths it, and the default is precise-mAh based so it's smooth. (The tooltip's "rate · past N-min average" indicates this window.)

Markers · guides · pinning

Hovering a curve pops a marker and value at that point. In ⚙ Settings, choose floor guides (time · date axes) and the value guide (to the vertical axis: diagonal / right-angle / dot / plane), and change the marker size. Click a point to pin it (📌) so you can rotate the angle by dragging while keeping it, and a pinned tooltip can be dragged to move it.
